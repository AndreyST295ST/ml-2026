## 2. Что было сделано

### 2.1. Синхронизация баз данных

Добавлен режим сравнения основной и входящей SQLite-базы. Для сущностей Forest формируется план изменений, в котором отдельно показываются:

- одинаковые записи;
- записи только в локальной или входящей базе;
- различающиеся значения;
- безопасные операции для применения;
- конфликты, требующие ручного решения;
- файлы кэша, отсутствующие на текущем компьютере.

Перед применением плана создаётся резервная копия базы. Результат синхронизации сохраняется в отчёты по операциям, пропущенным строкам и конфликтам. Проверка локального кэша отделена от сравнения логической разметки: одинаковые записи в БД не считаются различными только из-за того, что GeoTIFF или preview отсутствует на одном компьютере.

Для отсутствующих Sentinel-объектов в UI выводится отдельный список с выбором строк и массовой загрузкой. Операция выполняется как фоновая задача с отображением общего статуса и прогресса.

### 2.2. Событийная модель Forest samples

Ранее все снимки территории фактически связывались только с одним dominant year. Для поддержки нескольких событий добавлены таблицы:

- `forest_sample_events` — события потери леса для sample;
- `forest_sample_event_downloads` — связь события со снимком и его ролью `PRE`, `EVENT` или `POST`.

События строятся по распределению `lossyear` Hansen за 2016–2025 годы. Для каждого события сохраняются год, площадь потери леса, доля от общей площади потерь и признак dominant event. Один Sentinel download может участвовать в разных событиях и иметь разную временную роль относительно каждого из них.

В интерфейсе sample теперь отображается список событий по годам с площадью и долей потери леса. Выбор события меняет доступный PRE/EVENT/POST-контекст. Для старых загрузок подготовлен контролируемый backfill связей: сначала строится план, после проверки связи можно записать в БД с предварительным backup.

### 2.3. Data Operations и массовая загрузка Sentinel-2

В ResearchTool добавлен отдельный раздел `Data Operations`. В нём объединены операции, которые раньше требовали ручного запуска нескольких Python-скриптов:

- построение плана массовой загрузки Sentinel по событиям;
- выбор отдельных операций или всех подходящих строк;
- запуск и контроль фоновой загрузки;
- синхронизация Hansen events;
- подготовка export bundle;
- проверка и импорт входящего bundle.

План загрузки учитывает класс sample, событие, период, сезон, существующие снимки и результаты QC. Перед запуском пользователь видит, какие PRE/EVENT/POST-операции будут выполнены, и может снять отдельные checkbox-ы. После загрузки формируется selection-файл, который можно сразу использовать как источник для bundle, без промежуточного ручного редактирования CSV.

### 2.4. Переход к Sentinel cache bundle

Разметка и метаданные остаются в общей SQLite-базе, а тяжёлые растровые файлы передаются отдельно. Для этого реализованы три профиля bundle:

| Профиль | Содержимое | Назначение |
|---|---|---|
| `geotiff_only` | GeoTIFF и его metadata | основной компактный способ передачи |
| `preview_only` | готовые PNG/JSON preview | передача только производных изображений |
| `full` | GeoTIFF, metadata и все preview | полная копия локального кэша |

Основным выбран `geotiff_only`: шесть preview-слоёв (`RGB`, `False Color`, `NDVI`, `NBR`, `NDMI`, `SCL`) не дублируются в архиве, а пересчитываются на принимающей стороне из GeoTIFF.

Bundle содержит manifest версии 2 со списком `download_id`, относительными путями, размерами, checksum и связями снимков с событиями. Перед импортом выполняется dry-run: проверяются manifest, наличие строк в актуальной БД, identity-конфликты, доступность файлов и контрольные суммы. Если база получателя не содержит нужный `download_id`, импорт блокируется до синхронизации базы.

После успешной проверки импорт:

1. копирует выбранные файлы в проектный кэш;
2. использует проектно-относительные пути;
3. при необходимости пересобирает derived preview;
4. показывает прогресс и сохраняет итоговый отчёт.

CLI-скрипты экспорта и импорта сохранены как резервный способ работы, но основной сценарий теперь доступен прямо из UI.

## 4. Эксперимент с RemoteCLIP

### 4.1. Постановка эксперимента

Подготовлен новый событийный эксперимент для бинарной классификации `Logging` / `Wildfire` по RGB-снимкам Sentinel-2. Единицей анализа является не только sample, а пара `sample_id + event_year`. Это позволяет корректно работать с территориями, на которых Hansen показывает несколько событий разных лет.

RemoteCLIP `ViT-B-32` используется как фиксированный feature extractor. Для каждого изображения вычисляется нормированный 512-мерный embedding, после чего embeddings агрегируются по событию и периоду. Проверяются шесть вариантов признаков:

- `PRE`;
- `POST`;
- `DELTA = POST - PRE`;
- `PRE + POST`;
- `POST + DELTA`;
- `PRE + POST + DELTA`.

Поверх признаков обучается linear probe:

```text
StandardScaler + LogisticRegression(class_weight="balanced")
```

Основной вариант проверки — `StratifiedGroupKFold` с группировкой по `sample_id`. Поэтому события одной территории не могут одновременно попасть в train и test. Дополнительно оставлен обычный stratified split как диагностический вариант для оценки возможной утечки пространственного контекста.

### 4.2. Реализация экспериментального контура

Эксперимент оформлен в Jupyter Notebook, а загрузка данных, event backfill, inference, кэширование, splits и расчёт метрик вынесены в отдельные Python-модули. В notebook остаются параметры запуска, краткие англоязычные пояснения и визуализация результатов.

Реализовано:

- dry-run и безопасное применение backfill для legacy downloads;
- дисковый кэш RemoteCLIP embeddings с fingerprint изображения, checkpoint и preprocessing;
- повторное использование совместимых метрик после перезапуска notebook;
- сохранение одинаковых splits для сравниваемых режимов;
- отдельные когорты `MANUAL_VALID` и `NO_MANUAL_WEAK`;
- формирование очереди NoManual-событий с максимальным расхождением модели и WRI label;
- headless-запуск того же pipeline из Python-скрипта.

### 4.3. Результаты

Ниже приведены результаты быстрого профиля `5 folds × 1 seed`. Основной для интерпретации split — grouped, так как он не смешивает события одной территории между train и test.

| Признаки и режим | Accuracy | Balanced accuracy | F1 | ROC-AUC |
|---|---:|---:|---:|---:|
| `PRE`, manual only, grouped | 0.786 ± 0.028 | 0.797 ± 0.012 | 0.748 ± 0.016 | 0.916 ± 0.029 |
| `POST`, manual only, grouped | 0.881 ± 0.032 | 0.891 ± 0.031 | 0.854 ± 0.038 | 0.983 ± 0.015 |
| `PRE + POST`, manual only, grouped | 0.880 ± 0.068 | 0.894 ± 0.050 | 0.865 ± 0.065 | 0.989 ± 0.019 |
| `PRE + POST + DELTA`, manual only, grouped | **0.914 ± 0.054** | **0.927 ± 0.048** | **0.901 ± 0.062** | **0.991 ± 0.012** |
| `POST`, weak only → manual test, grouped | 0.864 ± 0.115 | 0.858 ± 0.117 | 0.822 ± 0.147 | 0.919 ± 0.077 |
| `PRE + POST`, manual + weak, grouped | 0.974 ± 0.021 | 0.965 ± 0.028 | 0.963 ± 0.030 | 0.999 ± 0.003 |

Основные наблюдения:

- `POST` заметно информативнее `PRE`, то есть после события в изображениях появляется дополнительный различимый сигнал;
- на вручную подтверждённой когорте лучший результат дал совместный признак `PRE + POST + DELTA`;
- обучение только на NoManual weak-когорте сохраняет перенос на manual test (`balanced accuracy = 0.858` для `POST`), но разброс пока велик;
- добавление weak-данных повышает метрики, однако этот результат нельзя считать финальной оценкой качества ground truth.

Важное ограничение: целевой класс `Logging` / `Wildfire` берётся из исходной WRI-разметки. Статус `Manual Valid` подтверждает наличие подходящего события, но не является независимой ручной перепроверкой класса. Поэтому текущий запуск проверяет согласованность визуальных признаков с WRI label и пригодность экспериментального контура, а не окончательное качество классификатора.
