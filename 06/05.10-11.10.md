# Отчёт о проделанной работе за неделю (05.10–11.10.2026)

## Тема проекта

**«Технологический трекер Hacker News»** — веб-сервис аналитики и прогнозирования популярности технологий на основе постов и комментариев Hacker News.

## Кратко

Неделя была посвящена эмбеддингам технологий. Корпус пересобран с исправленным токенизатором и обучен Word2Vec на заголовках с комментариями. Раньше качество модели оценивалось на глаз по спискам соседей, теперь появилась формальная оценка: проверка на вырожденность и набор проверочных пар технологий с метриками hit rate@k и MRR. Написан скрипт подбора гиперпараметров по сетке. Главный вывод недели: при параметрах по умолчанию модель на нашем объёме данных вырождается, и параметры нужно подбирать под размер корпуса.

## Проделанная работа

### 1. Подготовка корпуса для обучения
- Корпус «заголовок + комментарии» пересобран с исправленным на прошлой неделе токенизатором. Названия вроде `C++`, `C#`, `.NET`, `node.js` теперь попадают в словарь модели одним токеном (`cpp`, `csharp`, `dotnet`, `nodejs`) и совпадают с ключами словаря технологий.
- В `export_context` и `export_titles` добавлен флаг `--with-techs-only`: в выгрузку попадают только истории, где найдена хотя бы одна технология. Для эмбеддингов технологий остальные истории почти ничего не дают, но увеличивают корпус и время обучения.
- При этом истории без технологий больше не удаляются из БД (скрипт `trim` убран из основного конвейера). Они понадобятся позже как база сравнения при расчёте метрик вовлечённости: насколько статьи о технологии X обсуждаются активнее «обычной» статьи.
- Добавлена функция `tokenize_and_lemmatize_many`: пачка текстов токенизируется целиком, а новые слова всей пачки лемматизируются одним вызовом spaCy. Результат совпадает с построчной обработкой, это проверено тестом.

### 2. Оценка качества эмбеддингов
Раньше качество модели проверялось просмотром ближайших соседей для нескольких технологий. Это субъективно и не позволяет сравнивать модели между собой. Написан модуль `analytics/embeddings/w2v_quality.py` с двумя проверками:

- **Вырожденность.** Считается средняя косинусная близость между всеми парами технологий из словаря. На малом корпусе векторы технологий почти сонаправлены (близость около 0.99), и порядок соседей у такой модели — шум, хотя сами списки соседей выглядят правдоподобно. Если средняя близость выше 0.9, модель помечается как вырожденная.
- **Проверочные пары.** Составлено около 20 пар технологий из одной ниши, которые должны оказаться рядом:

| Ниша | Пары |
|---|---|
| Языки программирования | Rust — C++, Rust — Go, C — C++, Python — R, Python — Julia, Java — Kotlin, Java — Scala, JavaScript — TypeScript, Swift — Kotlin, Haskell — Elixir, Elixir — Erlang, Ruby — PHP |
| СУБД | PostgreSQL — MySQL, PostgreSQL — SQLite |
| LLM | GPT — Claude, GPT — Gemini, Claude — Llama |
| ОС | Linux — Windows, Windows — macOS, iOS — Android |

  Для каждой пары считается место второй технологии среди соседей первой (соседи ищутся только среди технологий словаря, а не среди всех слов). По этим местам считаются **hit rate@k** (доля пар, где вторая технология попала в топ-k, по умолчанию k = 10) и **MRR** (среднее 1/место).
- Отчёт о качестве теперь печатается сразу после обучения в `train_model`, поэтому вырожденную модель видно до того, как её результаты пойдут дальше по конвейеру.

### 3. Подбор гиперпараметров
- Написан скрипт `analytics.embeddings.scripts.tune_model`. Он обучает Word2Vec по сетке параметров (размерность, `min_count`, число эпох, размер окна; skip-gram или CBOW) и для каждой конфигурации выводит размер словаря, число найденных технологий, hit rate@k, MRR, среднюю близость и время обучения. Модели при этом не сохраняются, лучший набор параметров затем передаётся в `train_model`.
- Порядок ранжирования: сначала невырожденные модели, затем по MRR, а при равенстве выигрывает меньшая размерность (дешевле и меньше склонна к переобучению).
- **Результат.** На тестовом корпусе (около 20 тыс. items) параметры по умолчанию, которые мы использовали с первой недели (300d, 5 эпох), дают **вырожденную** модель. Модели с размерностью 50–100 и около 30 эпох технологии уже различают. Это объясняет шумные соседи у базовой модели на второй неделе: дело было не только в коротких заголовках, но и в слишком большой размерности и малом числе эпох для такого объёма.
- Проверочных пар всего около 20, поэтому разница в MRR на несколько сотых — шум. Окончательные параметры будем выбирать на полном объёме данных.

### 4. Агрегация синонимов
- После обучения векторы всех слов, которые соответствуют паттернам одной технологии (например, `postgres`, `postgresql`, `psql`, `psycopg`), объединяются в один вектор технологии. Используется среднее, взвешенное по частоте слов в корпусе, так что редкие написания почти не смещают вектор. Включается флагом `--aggregate-synonyms`.
- Агрегированные векторы сохраняются отдельно (CSV и текстовый формат word2vec) и будут использоваться для матрицы близости технологий.

### 5. Тесты
- Тесты для `w2v_quality`: правильный подсчёт мест, hit rate и MRR на игрушечных векторах, распознавание вырожденной модели, случай, когда технологий нет в словаре. Отдельный тест проверяет, что все проверочные пары состоят из технологий словаря.
- Тест для пакетной лемматизации: результат совпадает с построчной обработкой.

## Проблемы и риски
- Агрегация синонимов проверяет регулярные выражения на отдельных словах словаря модели. Многословные паттерны (`spring boot`, `arch linux`, `apache hive`) и паттерны с точкой (`.py`, `crates.io`) на одиночных токенах никогда не срабатывают. Поэтому для части технологий синонимы учитываются не полностью.
- Около 20 проверочных пар — маленький набор, причём составленный вручную. По нему можно отличить рабочую модель от сломанной, но тонкое сравнение двух хороших моделей он не выдерживает. Набор стоит расширить.
- Подбор по сетке на полном корпусе будет долгим: каждая конфигурация обучается заново. Сетку придётся сужать по результатам на подвыборке.
- Ручная оценка precision/recall словаря на случайной выборке заголовков, запланированная на эту неделю, не сделана: время ушло на метрики эмбеддингов. Переносится на следующую неделю.
